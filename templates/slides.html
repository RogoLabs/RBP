CVE Consumer Working Group

Reserved but Public

What a data consumer sees when a CVE ID is reserved, referenced in a public source, and still unpublished. Which is nothing.

{{ summary.total | commafy }} IDs are in that state right now, from {{ deck.feeds.configured }} public sources. Every figure in this deck was computed by the run that built the page.

rbptracker.org · Jerry Gamblin · built from the {{ snapshot_date }} run · {{ generated }}

Open with the count, not with the argument. This deck attributes no row to anyone and makes no claim about what anyone did or failed to do; it is a measurement of a state the CVE Program itself defines. If someone asks "whose fault is this", the answer is that the site cannot tell you, on purpose, and the boundaries slide says why.
{# ------------------------------------------------------------ 2. definition #}

The term is the Program's own

A state, defined by the glossary

A CVE ID in the “Reserved” state that is referenced in one or more public sources but for which a CVE Record has not been published. CVE Program glossary, “Reserved but Public”

What the advisory says. A distribution, a vendor or a repository publishes a fix and cites the ID. The vulnerability is public. The patch is public. The ID is in the changelog.

What the CVE List says. Nothing. Pull cvelistV5 and there are zero records in the RESERVED state, so a consumer joining on CVE ID gets an empty row and no signal that one is missing.

The bulk data is not wrong. Reserved records are not published by design, so the gap is structural rather than a defect in any one feed.

Read the glossary line verbatim. The point of leading with it is that nobody in the room has to accept a new definition from me. Then the two-column contrast: the advisory exists, the record does not, and the consumer is the one holding both halves.

{# ------------------------------------------------------------- 10. degraded #}

The failure a row count cannot see

A frozen feed returns a perfect number for ever

A feed that fails is easy: it throws, the run records it, the artefact says so. A feed that quietly stops updating returns the same healthy row count on every run, indefinitely, and every downstream check passes.

Generalise past this project: any consumer aggregating third-party feeds has this failure mode and most do not check for it. Freshness of the newest record, not row count, is the check. {# ------------------------------------------------------------ 13. boundaries #}

Stated plainly, because it limits the claim

What this is not

  • Not a count of violations. It is a count of a state. Rows include IDs inside a coordinated disclosure and IDs whose record is in flight. RBP Policy v2.0.0 also lets a Root direct a CNA-LR to publish a record for an ID it did not assign, so a party can hold an ID precisely because it is a CNA-LR, and nothing observable distinguishes an ID accepted for a third-party requester from one withheld by its assigner.
  • Not a scorecard. No row here is attributed to anyone. The reservation API redacts the owner for every reserved ID, so ownership could only be estimated, and an estimate is not a thing to publish beside a name. The site does publish the aggregate coverage set, which CNAs its feeds can see at all, in /data/summary.json. That is deliberate: the reach figure earlier is not auditable without it. It is a statement about this site's reach, and it attributes no CVE ID to anybody.
  • Not a total. A floor, bounded by {{ deck.feeds.configured }} feeds and by the measured reach.
  • Not comparable run to run while the feed set is still changing.
  • Not an argument about the Program. The definition is the Program's own and the measurement is taken from outside it.
If the room pushes for names, the answer is that the enforcement of no-attribution is structural rather than editorial: one flag at the writer, one definition of what counts as a name, a staging check that refuses any tree containing a certified short name, and a test asserting the inference module is not even importable from the publish path.

What I would like from this group

Four questions

  • Is this state representable in your tooling at all? Most consumer schemas have published and withdrawn. Reserved-and-publicly-referenced is usually a null row rather than a state.
  • Which sources are missing? The count is a floor bounded by the feed list. Every source added raises it, and the admissibility rules are published.
  • Is a stable machine-readable feed of this useful to you, and in what shape? The files exist today; the schema is v{{ schema_version }} and the versioning is deliberate.
  • What would you want a consumer-facing convention to say about an advisory that cites an ID with no record behind it?
