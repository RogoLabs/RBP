What is a Reserved but Public CVE ID?

A Reserved but Public CVE ID is one a CNA has reserved and that appears in a public advisory, while the CVE Record itself is still unpublished. Anyone pulling the CVE List sees nothing. The advisory is already out there.

The term is the CVE Program's own. Its glossary definition reads:

A CVE ID in the “Reserved” state that is referenced in one or more public sources but for which a CVE Record has not been published.

What the policy expects

RBP Policy v2.0.0, approved by the CVE Board on 13 August 2026, expects a record within 72 hours of disclosure, and sets out a real process: a Root notifies the CNA with a remediation timeline, CNAs must prioritise requests to publish critical RBPs, and repeat failures escalate up to decertification. That process runs inside the Program and is not visible in public data, so this site reports the state rather than the response to it.

Why no CNA is named here

The state itself is observable, and the CVE Services API will confirm it. What it will not tell you is who reserved the ID: "owning_cna": "[REDACTED]". CNA Rule 4.5.1.7 both permits and limits naming, and it binds the Secretariat rather than anyone else:

The Secretariat MAY publicly identify the CNA who reserved the CVE ID 24 hours after a CVE ID has been Publicly Disclosed. Otherwise, the Secretariat SHOULD NOT publicly identify the CNA until the CVE Record has been published.

So this site lists the identifier and the advisories it appears in, and leaves attribution to the Program. Ownership can be estimated from public data, and this version does not publish those estimates: the same reasoning that recovers an owner for a referenced ID would work across the whole reserved space, which is a good reason for the redaction to stay as it is.

The Program used to publish this

The Program used to publish a count of these. A quarterly table ran on the CVE Metrics page and was commented out in February 2022, as item 2 of a three-item quarterly-to-annual table restructuring (cve-website #842), a fortnight after the v1.0 policy PDF was withdrawn to be “replaced with a new version of the document at a later date” (#835). That replacement is now v2.0.0. The series has not resumed. Its final column already read N/A, so it had stopped being populated before anyone commented it out.

This site will not be that series, and is not comparable to it. That table was a quarterly flow of newly identified RBPs, measured with authoritative internal access, falling from 4,326 in Q1 2017 to 350 in Q3 2021. What is being built here is a live stock, discovered from downstream advisory feeds that reach a minority of CNAs, with the owner inferred rather than known. Both numbers would be real. They would not be the same measurement, and neither replaces the other.

RBP Policy v2.0.0 names “Program metrics and audits” as one of the Program's own channels for identifying RBPs. If the Program publishes a figure of its own it will be measured with internal access, and this one is not a substitute for it.

What this measures, and what it does not

This is a Program-level transparency measurement, not a CNA scorecard. Which CNAs appear here is decided by how wide their ID blocks are and whether this site reads their advisories, not by how they behave: a CNA with large contiguous blocks and feeds we ingest is nameable, and one with neither is invisible no matter what it does. RBP Policy v2.0.0 also lets a Root direct a CNA-LR to publish an overdue record, so a row may be an ID delegated to a CNA rather than withheld by it, and nothing observable from outside distinguishes the two. What the policy says in the CNAs' favour

This site quotes the policy's hardest line at the top of this page. The same document carries four passages that cut the other way, and this project's own standard is that quoting only the parts that suit us would be selective. They are reproduced verbatim below, under the section headings they actually occupy, because two of them are not in Timely Publication and filing them there would misdescribe the policy.

Timely Publication

CNAs should ensure timely publication of CVE Records, “recognizing that such publication may, at times, coincide with ongoing vulnerability or incident response activities.”

“The CVE Program recognizes that internal processes may necessitate short delays; however, time flexibility allowed by the CNA Operational Rules should not be used to intentionally delay publication once an advisory or Fix has been made public.”

Notification and Remediation

The CNA is expected to publish RBPs as soon as possible and “no later than the deadline stated by their TL-Root or Root (which may account for factors such as volume, complexity, and resource constraints).”

Enforcement

“The CVE Program may take further action depending on the CNA's volume, history, and severity of RBPs.”

Taking those seriously changes what this site can claim, and it already has. Nothing is listed until it has been public for {{ summary.get('min_age_days', 7) }} days, which is {{ ((summary.get('min_age_days', 7) * 24 / expectation_hours) | round(1)) }}x the {{ expectation_hours }}-hour window and well past any short delay or live incident response. The median row here has been public {{ summary.median_days }} days, and {{ summary.age_buckets.get('180d+', 0) }} have been public more than 180 days. A short delay is not what this list is measuring.

And the last two passages license the sentence this whole site is built around: the only deadline that binds a specific row is one a Root set privately. It accounts for volume and resource constraints, it is not published, and no outside observer can see it. That is precisely why this site measures days public and never calls a single row overdue.

How this is measured

Ten public advisory feeds are read every six hours and everything they reference is checked against the CVE List. Nothing appears here until it has been publicly referenced for at least {{ summary.get('min_age_days', 7) }} days, which is {{ ((summary.get('min_age_days', 7) * 24) / 72) | round(1) }}x the 72-hour expectation, so ordinary latency and short coordinated-disclosure windows are excluded.

The feeds reach a minority of CNAs, so every number here is a floor, never a census. The method in full, and the policy quotations.

If a row should not be listed

Email rbp@rogolabs.net giving the CVE ID and nothing else. No reason, no detail, no confirmation that a vulnerability exists: a request naming only an identifier does not distinguish an embargo from a wrong row, and asking for a reason would make the request itself a disclosure. Read by a person.
