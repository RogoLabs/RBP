That is the CVE Program's own definition, quoted from RBP Policy v2.0.0 and still <a href="https://www.cve.org/ResourcesSupport/Glossary?activeTerm=glossaryRBP">live in the cve.org glossary</a>. </p> <p> <strong>RBP is a state, not a verdict.</strong> The policy defines the state on its own terms, then separately conditions its notification steps on an RBP “in violation of Program Rules 4.5.1.4 or 4.5.1.6 exceeding the 72 hours”, and assigns that determination to Roots, TL-Roots and the Secretariat. The headline count on this site is the state, which makes it the Program's own <strong>definition</strong>, measured from outside. Violation language is confined to the rule column, always marked candidate, and never aggregated into the headline. </p> <p> State comes from the CVE Services reservation endpoint, which returns it directly: </p> <pre class="api">GET https://cveawg.mitre.org/api/cve-id/CVE-2026-2574 {"cve_id":"CVE-2026-2574","cve_year":"2026", "state":"<strong>RESERVED</strong>","owning_cna":"<strong>[REDACTED]</strong>"}</pre> <p> This matters because the more commonly used <span class="mono">/api/cve/</span> endpoint returns 404 for a reserved ID, making it indistinguishable from an ID that was never allocated. Using the reservation endpoint instead means a row here is a confirmed reservation and not an inference about absence. IDs that were never allocated return <span class="mono">CVE_ID_NOT_FOUND</span> and are excluded. That screens IDs that do not exist. It does not screen a mistyped ID that happens to land on a real reserved neighbour, which passes every check this site makes, so some small number of rows are likely transcription errors in the citing advisory rather than genuine RBPs. </p> <p class="mb-0"> The bulk CVE List contains <strong>zero</strong> reserved records, and the cvelistV5 git tree carries none either, so no tool sourcing only from those can see any of this. </p> </div> </div> {# The cadence card and the standing-limits card moved to /status on 2026-08-26.
